# Cluster Digest (dash.local)

A version-drift dashboard that shows what's running against what's available, for every
HelmRelease and for a chosen list of raw-manifest images. It's LAN-only
(`http://dash.local:30080`), with no auth and no public route. It **only shows** drift and never
upgrades anything. Upgrades still happen by editing this repo.

| Piece | Detail |
|---|---|
| Dashboard | `digest-dashboard` (nginx 1.30.7-alpine, 10m CPU / 32Mi) serving one static page that fetches `/status.json` from the PVC. **Never go below nginx 1.30.7** (CVE-2026-123007/Nginx2Shell) |
| Worker | CronJob `digest-worker` (alpine/k8s:1.37.2) on **Saturdays at 04:00, even ISO weeks only**. CronJob schedules can't express "every two weeks", so the script exits on odd weeks |
| Storage | `digest-data` (100Mi local-path) holding `status.json` and `history.jsonl` (one summary per week, at most 52) |
| RBAC | read-only ClusterRole (helmreleases, helmrepositories, deployments), plus a flux-system Role restricted by `resourceNames` to `forgejo-registry-auth` |

## How versions are resolved

- **HelmReleases:** the running version is `status.lastAttemptedRevision`. The latest is the newest
  stable version in the release's HelmRepository.
  - HTTP repos: parsed from `index.yaml` with awk. The first entry isn't always the newest stable
    one (cert-manager lists alphas at the top).
  - OCI repos: through the registry tag API (`registry-1.docker.io`, `ghcr.io`, `codeberg.org`,
    `fgit.watchtoken.org`). The private cv-datastar chart resolves through `forgejo-registry-auth`.
  - A HelmRelease whose `spec.chart.spec.version` is a range (`0.x`, `*`) is labelled
    `auto-follow`.
- **Raw images:** the list is `raw-images.yaml`, with `name`, `image`, `ns` and an optional
  `note: pinned`.
  - The running tag comes from the live Deployment, including `initContainers` (gluetun lives
    there).
  - The latest version comes from the `:latest` manifest's `org.opencontainers.image.version`
    label when the image sets one. LSIO images do, which gives the exact `<version>-ls<N>` build
    without paging through thousands of tags. Otherwise it falls back to a paged tag list.
  - Images marked `note: pinned` (jellyfin) are never compared.
- **Bump size:** major, minor or patch from the numeric fields. LSIO build numbers (`-ls<N>`,
  including compound tags like `5.3.0_v2.1.2-ls487`) count as a fourth component. Tags that can't
  be compared (such as jellyfin's `version-12.4ubu2604`) show `unknown` rather than a false
  "outdated".

## Editing

The ConfigMaps are generated by kustomize `configMapGenerator`. Edit `scripts/worker.sh`,
`raw-images.yaml`, `nginx.conf` or `index.html` and commit. The content-hash suffix in the
generated ConfigMap name changes, so Flux restarts the dashboard Deployment and the CronJob's next
pod picks up the change. Never write the ConfigMaps by hand.

## Verify

```bash
kubectl -n cluster-digest get pods,cronjob
curl -s http://dash.local:30080/status.json
# or: kubectl -n cluster-digest exec deploy/digest-dashboard -- wget -qO- localhost:8080/status.json
```

The page shows a stale-worker warning if `generated` is more than 16 days old. That's the one way
it can fail without anyone noticing (the worker stopped running). To force a run after a merge:
`kubectl -n cluster-digest create job --from=cronjob/digest-worker manual-$(date +%s)`. The
every-two-weeks check still applies, so on odd weeks the job exits right away by design.
